<react_19_ref_pattern>
<!-- LOCKED for this project — verified against react.dev/blog/2024/12/05/react-19#ref-as-a-prop and shadcn/ui new-york-v4 registry on 2026-04-27. -->

React 19 deprecated `React.forwardRef`. The canonical pattern is now to accept `ref` as a regular destructured prop. Every component in this plan follows the same shape:

```typescript
import * as React from "react";

function MyComponent({
  className,
  ref,
  ...props
}: React.ComponentProps<"button"> & { /* extra typed props */ }) {
  return <button ref={ref} className={cn("...", className)} {...props} />;
}

export { MyComponent };
```

Key rules:
- `React.ComponentProps<"button">` (or `<"div">`, `<"section">`) ALREADY includes `ref` in its type union in React 19's typings — you don't need to type ref separately, just destructure it.
- The function is a plain `function` declaration (not `React.forwardRef(...)`).
- Export the function via a named export at the bottom (matches shadcn's new-york-v4 style).
- Do NOT set `displayName` — for React 19 plain function components, the function name IS the displayName. Setting it manually is a smell.
- Do NOT wrap in `React.memo` unless profiled — premature optimization.

If you find yourself reaching for `React.forwardRef`, STOP — re-read this block. The acceptance criteria explicitly grep for `forwardRef` and fail if found.
</react_19_ref_pattern>

   ```tsx
     variant,

     ...props
   ```

   - `data-slot="button"` is the shadcn new-york-v4 convention — used by future composition (e.g. ButtonGroup) and by Radix-aware tools. Cheap and harmless.

   ```tsx
   import { cn } from "@/lib/utils";

   export interface SectionProps extends React.ComponentProps<"section"> {
     /**
      * Render as a different element when semantics demand it.
      * - "section" (default): generic semantic section — covers all 7 page-1 blocks
      * - "div": rare; use only when this wraps something that ALREADY has its own semantic role
      *   (e.g. inside a `<main>` already, with no h2 of its own — like the header/footer in the smoke-test)
      *
      * Constrained to the literal union "section" | "div" at the prop boundary. Internally we cast
      * to React.ElementType for the JSX render, which loses the constraint at the runtime React type
      * level — acceptable for Phase 1 since the prop-level union prevents callers from passing other
      * elements. Phase 2 may refine if we need true element-level type discrimination
      * (e.g. via generics over the `as` type), but for one prop with two valid values it's overkill.
      */
     as?: "section" | "div";
   }

   /**
    * Vertical-rhythm wrapper for a page block.
    *
    * Padding (locked in 01-CONTEXT.md):
    * - mobile (default): py-16 (64px)
    * - md (768px+): py-24 (96px)
    * - lg (1024px+): py-32 (128px)
    *
    * Pair with `<Container>` for horizontal gutters and max-width:
    *   <Section id="hero">
    *     <Container>...</Container>
    *   </Section>
    *
    * React-19 native: pass `ref` directly as a prop, no forwardRef wrapper.
    *
    * Type-safety note: the `as` prop is constrained to "section" | "div" at the prop level;
    * other elements are rejected at compile time. We cast to React.ElementType internally
    * for JSX rendering — Phase 1 accepts this minor loss of type discrimination since the
    * prop-level union is a sufficient guard for our two valid cases.
    */
   function Section({
     className,
     as = "section",
     children,
     ...props
   }: SectionProps) {
     const Component = as as React.ElementType;
     return (
       <Component
         data-slot="section"
         className={cn("w-full py-16 md:py-24 lg:py-32", className)}
         {...props}
       >
         {children}
       </Component>
     );
   }

   export { Section };
   ```

   **Why these decisions:**
   - `extends React.ComponentProps<"section">` — this picks up React 19's `ref` prop type AND every standard HTMLSectionElement attribute (id, role, aria-*, etc.). We don't need to redeclare `id` because `ComponentProps<"section">` already includes it. SectionProps has an additional `as` field, so the interface form is correct here (not flagged by `no-empty-object-type`).
   - The `as` prop default is `"section"` because that's the actual locked decision; the escape hatch to `"div"` exists for the rare case (header/footer in the smoke-test, which are wrapped in Section-as-div for vertical rhythm without claiming to be a `<section>` semantically). The `as React.ElementType` cast is documented in the JSDoc above the prop and on the function — Phase 2 may refine if true generic element-discrimination becomes needed, but the literal-union prop guard is sufficient for the two valid values in Phase 1.
   - `w-full` is critical — without it, `<Section>` collapses if its parent is `inline-block` or `flex` with shrink. The 7 sections in Phase 2 will be direct children of `<main>`, so `w-full` ensures full-width backgrounds (e.g. a muted-bg section breaks the page rhythm correctly).
   - We do NOT add horizontal padding here — that is `<Container>`'s job. Mixing them locks the box model in a single way; if a future Phase wants a full-bleed section (image edge-to-edge) it can use `<Section>` without `<Container>` and add a smaller inner wrapper.
   - `data-slot="section"` matches shadcn new-york-v4 convention for downstream tooling.
   - We accept `ref` implicitly via `...props` spread to the underlying element. If a Phase 2 author wants to attach a ref for scroll-to-section, `<Section ref={mySectionRef}>` works naturally.
